# Backend releases

The plugin's default backend is built from the upstream commit and toolchain recorded in `lib/backend-release.json`, with `patches/argon.patch` applied. The builder overrides the backend's displayed version with the release version. Six binaries are pinned by SHA-256 in the same JSON file. The build does not include the developer's uncommitted backend sources, local data or credentials.

For a new backend release:

1. Choose a new backend version and tag in `lib/backend-release.json`. Never replace files under an already published backend tag: older plugins pin those hashes. Update the upstream commit or patch when needed.
2. Run `node scripts/backend-release.mjs --write-pins`. It extracts a clean upstream tree, applies the patch, runs Go tests, cross-compiles all six targets and writes the resulting pins. It uses a local `backend-source` Git object database if available; otherwise it fetches the pinned public commit in a temporary directory.
3. Run `npm test`, `node scripts/backend-smoke.mjs`, and `node scripts/backend-persist.mjs`. Smoke uses a temporary data directory and deletes it when finished. It checks the executable's version and hash, starts it on a spare loopback port, checks authentication and model discovery, and verifies reuse. It is not a persistent install. `node scripts/backend.mjs install-local --data-dir=<path>` copies the host artifact from `backend-build/release` only after its SHA-256 matches the committed pin. The artifact is read once and only those verified bytes are installed, so a parallel build replacing the file cannot slip past the check; a failed install keeps the previous binary and `backend-channel.json`. It does not download and does not delete the directory. The persist script proves that with two processes: the installer exits, then a second process starts the same directory with downloads forbidden. Neither script uses a Google account. The tokenizer is forced onto its offline fallback. Until tag `backend-v4.31.0-magpie.1` is published, `npm run backend:install` fails because that GitHub asset does not exist yet; enable locally without downloading by running `node scripts/backend-release.mjs --target=host --verify`, then `node scripts/backend.mjs install-local --data-dir=<absolute path>`, and starting Magpie with `GEMINI_WEB_DATA_DIR` pointing at that same absolute directory. Smoke stays a temporary acceptance check. Do not pass `--download` to smoke before the tag is public.
4. Commit the release metadata, installer changes, tests and documentation. Run the **Verify backend release** GitHub Actions workflow at that commit. It rebuilds on native macOS, Linux and Windows runners for both architectures, compares the pinned hashes, and runs the installation/startup smoke test. Wait for all jobs to pass.
5. Create a private draft under the pinned backend tag. Attach all six binaries, `SHA256SUMS.txt`, `build.json`, the patched source archive and `LICENSE-UPSTREAM` from `backend-build/release`. If local binary uploads are unreliable, run **Upload verified backend release** with the successful verification run ID: it downloads the six CI artifacts, checks every committed hash, and uploads missing executables to the draft (`scripts/backend-draft.mjs` implements the reconciliation). Published releases cannot be modified by this workflow, and nothing already in the draft is re-uploaded. On a resumed run the source archive is not gzip-reproducible, so an existing draft copy is accepted only when its uncompressed content matches the rebuild; the draft's own bytes are then retained, and `SHA256SUMS.txt` is generated from the bytes actually retained. A `SHA256SUMS.txt` already in the draft must agree line by line with those retained bytes — a disagreement fails the run instead of replacing the manifest. Include the upstream commit and patch SHA-256 in the release notes, then publish the complete draft. Keep backend-only releases from replacing the plugin release as GitHub's latest release.
6. Verify public asset downloads against the committed pins. Run `node scripts/backend-smoke.mjs --download` to test the actual default download URL on the host platform.
7. Bump and publish the plugin package only after the backend assets are publicly available. Inspect `npm pack --dry-run`; the npm package contains release metadata and patch/build scripts, but no executables, local databases or credentials. Attach the exact published npm tarball to the plugin's GitHub release as well.

Reproduce a release without changing its pins:

```bash
npm run backend:release:build
```

Build just the host target and compare its hash:

```bash
node scripts/backend-release.mjs --target=host --verify
```

The metadata records `CGO_ENABLED=0`, the exact Go toolchain, upstream commit, patch hash and build flags. The binary hashes are reproducible; the source archive is supplied for inspection and is not promised to have a reproducible gzip timestamp. The source archive includes upstream's license, and `LICENSE-UPSTREAM` is also supplied as a separate asset.

Existing running processes are left alone to avoid interrupting requests. Once an old official backend is stopped, automatic startup installs the optimized build while preserving configuration, secrets and the database. A download or checksum failure keeps the old file and never starts an unverified replacement.

New cookie imports require the running backend to advertise `capabilities.account_proxy_binding: true` at `/`. The plugin checks this before changing the proxy pool and again before submitting a cookie, so a reused older or upstream backend cannot silently ignore `proxy_id`. Unsupported builds receive instructions to stop the old process and run the installed plugin's CLI with `install --data-dir=<path>`. This explicitly selects the optimized channel, including for previous upstream or custom-build installations. The check does not interrupt existing conversations. Release smoke verifies the capability and actual proxy selection; version strings alone do not establish support.

An explicit `npm run backend:install:upstream` installs the pinned upstream v4.31.0 and persists `upstream` in `backend-channel.json`. Automatic startup respects that choice. `npm run backend:install` returns to the optimized channel. Stop a running backend before replacing it, particularly on Windows. Explicit local Argon builds remain trusted through their existing build manifest.

Two timers apply to the optimized StreamGenerate path, and they are not the same event. `request_timeout_sec` (default 180, maximum 1200 seconds) is byte silence: any received byte, including a fragment or heartbeat, refreshes it. When it fires the error is a stall, and `retry_on_timeout=false` stops the retry. `stream_idle_timeout_sec` (default 0, off) is complete-line idle: only a read that contains a newline refreshes it. Fragments keep the stall timer alive but do not refresh this one. When it fires the error is an idle timeout, which is still retried when `retry_on_timeout` is false, and it is not recorded as a proxy failure. A turn that has already produced output is not replayed. The shorter timer wins. The official `processSession` path does not install the idle timer. An existing `default_model` of `gemini-3.1-pro@think=2` in `config.json` or the panel database routes to the normal tier of 4 Neon. The legacy suffix is ignored. `gemini-4-carbon` and `gemini-4-argon` are one mode-8 route. A same-family normal-tier display name after the anti-hang slot is accepted. A different family, such as 3.5 Flash-Lite or 4 Hydrogen, is rejected.

These behaviors still need a signed-in Google account before they can be treated as confirmed upstream behavior: whether a real High request still answers at the normal tier, the live heartbeat interval, and the display name if Google renames the family again. Do not use a real account for the automated smoke or persist checks.
